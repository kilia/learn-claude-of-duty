Harbor：改 Splash 速率 → Critic A/B 失效 → Fork 隔离闪电 / 雪

这是仓库里把「Build → Critic → Fix」与「随机流副作用」绑在同一条因果链上的真实病例。 Build agent 在同一条顺序 RNG 上生成雨、水花与闪电；某次只调 splash rate 的 Fix， 却让 lightning 截图拍到另一场雷——Critic 的指标动了，原因却与被测改动无关。 最终 Fix：fork 出独立流，新能力（雪）只追加在构建序列末尾， 且绝不重排 harbor 已冻结的雨块顺序。

1. Art Direction 原文（Cold Harbor）

Build / Critic 共用的视觉合同来自 ART_DIRECTION_HARBOR.md——不是“下雨好看一点”，而是可验收的画面。

The shot we are chasing

A container terminal at two in the morning, in driving rain. Sodium lamps on tall masts throw hard orange cones through the downpour — you can see the rain falling through the light. Everything is soaked: the concrete apron is a black mirror holding stretched reflections of every lamp, and the puddles ripple as drops hit them. Stacked shipping containers form dark canyons in faded red, blue and green, their corrugated flanks streaked with rust weeping from every weld. A gantry crane looms overhead, its legs disappearing into low cloud. Beyond the quay edge, black water and the hull of a moored freighter. Every few seconds, lightning flashes the entire scene cold blue-white for a fraction of a second, freezing the rain mid-air and throwing hard shadows in a completely different direction from the lamps — then it is dark again and your eye has to re-adapt. — ART_DIRECTION_HARBOR.md · “The shot we are chasing”

Wet is the whole look. Level 1 用尘卖大气；本关用水：反射、高光、对比承担原先 haze 的工作。

Lighting recipe（non-negotiable）

ElementValue
Ambient skyVery low, cold. Overcast storm cloud, no stars, no moon disc
PracticalsSodium mast ~2000K deep orange; mercury/LED floods ~5600K cold
Practical falloffHard. Pools of light with genuine darkness between them
Lightning3–8s interval, 60–180ms, cold ~7000K, varying direction, casts real shadows
FogDense low fog + rain scatter. Lamp cones must be visible volumetrically
Contrast / ExposureHIGH near-blacks OK but never crushed to zero · mean luminance ~0.10–0.18
Single most important effect： light cone through rain。 倾盆大雨里桅杆灯没有可见体积光锥 = 直接 fail。

Instant-fail list（艺术方向硬拒收）

  • Rain as a flat 2D screen overlay
  • Lamps with no visible volumetric cone in the downpour
  • Wet ground that is not reflective, or reflections that are just a blur
  • Lightning as a full-screen white fade with no directional shadow change
  • Containers that are flat-coloured boxes with no corrugation / rust / hardware / stencils
  • A flat, uniformly-lit scene — this level lives on pools of light and darkness
  • Crushed pure-black shadows with no detail whatsoever
  • Reusing the market's warm ochre palette
  • Puddles that do not ripple in the rain

全文：ART_DIRECTION_HARBOR.md · 另见 ARCHITECTURE.md §9 Quality bar（COD 对照即时拒收项）

本案例与艺术方向的交点：闪电必须是可复现的方向光事件 （bearing / elevation / distance → flashDir + 真阴影）。 若 splash 调参悄悄换了一场雷，Critic 就无法判断闪电是否满足 “varying direction, casts real shadows”——A/B 评的是另一张图。

2. Published Contracts（谁写、谁读、写什么）

三个互相咬合的合同：Weather API · Art-dir 交付物清单 · 确定性 / RNG 纪律。

API Weather 模块头注释（权威实现合同）

GAME.Weather owns the weather contract；其它系统只读不写。每个字段在每个 preset 上都存在且为有限数。

Field语义
weather.wetness0..1 全局表面湿润
weather.rainIntensity0..1 仅液态降水（暴雪里必须为 0，否则雪关会变成湿沥青）
weather.windDirTHREE.Vector2，归一化（x=world X, y=world Z）
weather.windSpeedm/s
weather.flash0..1 本帧闪电强度（多数帧为 0）
weather.flashDirTHREE.Vector3，指向闪光；与 sky.sunDirection 同约定，可做 Lambert
weather.fogDensity当前天空暗示的消光系数（per-metre）
weather.setPreset(n)'clear' | 'storm' | 'drizzle' | 'blizzard'
weather.strike()立刻强制一次闪电（捕获确定性）

可选扩展（precipitation-kind agnostic；旧消费者仍可只读上面七项）：

Field语义
weather.snowIntensity0..1 固态降水
weather.precipIntensitymax(rain, snow) — “下得有多猛”
weather.precipitation'none' | 'rain' | 'snow'

art direction 要求 Weather 必须交付的效果

来自 ART_DIRECTION_HARBOR.md · Weather contract · “Required from weather.js”：

determinism 确定性 / RNG 合同（本病例直接违反又修好的那条）

条款出处 / 含义
禁止 Math.random() DEVELOPMENT.md / ARCHITECTURE.md — 捕获必须可复现，否则 critique 无价值
同 seed → 同帧 Capture API：?scenario=&level=&t=&seed= 固定 1/60 推进到 t
子系统 fork(salt) 不推进父流 util.js · weather 用 lrng/srng 隔离闪电与雪
雨构建顺序冻结 harbor 原序；重排会移动每个 drip edge / splash
新能力末尾追加 snow 挂在序列尾，且走独立 srng
Market canary 非 harbor 上 weather 为 clear/absent，不得让共享改动污染 L1 帧
合同如何咬合：Art Direction 要求闪电“方向变化 + 真阴影”； Weather API 用 flash/flashDir/strike() 发布； RNG 合同保证同 seed 下这些方向可复现。本病例打断的是第三环—— splash 多抽导致 flashDir 序列漂了，前两环的验收全部落空。

对本病例，Critic / Verify 会写成什么样的 finding

severity: critical
file:    src/fx/weather.js
issue:   Changing splash rate moves lightning
         bearing/elevation/distance in the
         `lightning` capture; analyze.py deltas
         are not attributable to splash.

         forked RNG (do not share the splash
         stream); freeze rain build order.

对照 Art Direction 的验收点

  • 闪电非全屏白闪（instant-fail）
  • flashDir 可变且投阴影
  • 同 seed 重拍方位稳定 → 才能评体积光锥 / 湿反射
  • Splash 密度可调而不毒死上述任一条款

ARCHITECTURE §9 Quality bar（全局即时拒收）

  • Flat untextured or single-color surfaces
  • Visible texture tiling/repetition
  • Hard-edged aliased shadows, or shadow acne
  • Blown-out or crushed exposure
  • Gun that looks like grey boxes · Muzzle flash that is a white sphere
  • Enemies that are capsules or stiff mannequins
  • Empty geometry with no props, clutter, or wear
  • Perfectly straight, perfectly clean, perfectly uniform anything
  • Static, dead lighting with no atmosphere/depth cueing

Aim for: grounded, gritty, photographic, with atmospheric depth.

4. Build → Critic → Fix 时间线

角色拆开：生成者、审查者、修复者；证据是可复现截图，不是“感觉更好了”。

  1. BUILD

    港口天气系统落成

    Weather 从 ctx.rng.fork(0x5741) 拿到本模块流，按固定顺序构建雨相关资源， 闪电日程也从同一条 this.rng 抽方位 / 仰角 / 距离。

    • 产出可捕获的 lightning / 雨景 framing
    • 同一 seed → 同一帧（当时以为如此）
  2. CRITIC

    审查 / A/B：splash 调参轮

    Fix 意图只改水花密度。Critic（或 verify）重拍 lightning，跑 analyze.py。 指标移动、构图里雷的方位变了——看起来像“画面退步”。

    • 表面结论：改 splash 伤了闪电观感
    • 真正问题：两条捕获不是同一场雷 → A/B 无效
  3. FIX

    结构修复，不是再抽一次运气

    不搜“更好的 seed”。在构造函数里、任何 next() 之前：

    • this.lrng = this.rng.fork(0x71A5) — 闪电专用流
    • 稍后 this.srng = this.rng.fork(0x53A0) — 雪花专用流
    • 雨块调用顺序原样冻结；雪只挂在序列末尾
  4. VERIFY

    再验证：同 seed 同雷

    再改 splash rate / flake count，lightning 方位应字节级稳定； 加雪的那一行 fork 不得移动 harbor 已有 drip / splash 的任何一抽。

这与关卡美术 Critic（art director 打分）是同一方法论的不同镜头： 证据必须可复现。RNG 串流一旦污染，Critic 再狠也在评“另一张图”。

5. Critic 看见了什么（症状）

源码注释里的原话——这是写进 weather.js 的疤痕组织。

改之前 · 共享顺序流

Splash emitter 每帧从主 RNG 抽数十次。闪电日程也吃同一条流。

调高 splash rate → 每帧多消耗 N 次 next() → 闪电读到的第 k 个样本整体错位。

Critic / 度量读数

两张 lightning 捕获（改 splash 前后）：

  • 雷的 bearing / elevation / distance 全变
  • analyze.py 数字跟着动
  • 审查者以为 splash 改坏了闪电
误判：“splash 调参导致闪电回归。”
正解：“你根本没有在 A/B 同一个 strike；度量在比较两场不同的雷。” 
Every strike used to be drawn from the same RNG the splash emitter pulls from
tens of times a frame, so changing the splash RATE — a completely unrelated
tuning value — silently changed the bearing, elevation and distance of the
strike a capture would photograph. Two `lightning` frames taken either side
of a splash tweak were not an A/B of the splash tweak, they were two
different strikes, and the metrics moved for a reason that had nothing to
do with the edit.

摘自 src/fx/weather.js · Weather 构造函数注释

6. 顺序流污染 · 交互示意

点「增加 Splash 抽取」看闪电令牌如何被挤到别的值——这就是副作用扩散。

同一条流 · 同一种子 · 只改消耗次数

基准流 · splash×3 之后读闪电参数

splash 抽取 闪电参数（应稳定） 错位后的“假闪电”
Splash 消耗 闪电读到的流位置 捕获是否可比
基准 3 × next() index 3,4,5 → 方位 A 可作对照基准
只加 splash 6 × next() index 6,7,8 → 方位 B 不可比（另一场雷）

7. Fork：如何避免副作用

fork(salt) 从当前状态派生新种子，不推进父流。

RNG.prototype.fork = function (salt) {
  return new RNG((this._s ^ Math.imul(salt | 0, 0x9E3779B1)) >>> 0);
};

// Weather 构造函数 — 在第一次 next() 之前分叉
this.rng  = ctx.rng.fork(0x5741);
this.lrng = this.rng.fork(0x71A5);  // 闪电
this.srng = this.rng.fork(0x53A0);  // 雪

实现：src/core/util.js · 用法：src/fx/weather.js

关键性质：fork 派生新 RNG，读取当前 _s 做异或， 不调用父流的 next()。因此「多写一行 fork」本身不会让 harbor 已有抽取错位。

Fix 之后 · 两条流互不干扰

S1S2S3 S4S5S6 主天气流
L.bearingL.elevL.dist lrng · 始终同一序列

8. 修改落在末尾：不重排、不多插中间步骤

即便有了 fork，雨块仍是一条共享顺序流——插入或重排照样毒死整关。

Harbor 雨构建管线（冻结）

1roofMask
2rain
3splash
4drips
5mist
6ripples
7channel
+尾snow / snowAir

虚线框 = 原 harbor 序列，注释要求 same calls, same order, same yield points。 绿色强调 = 雪作为新能力追加在末尾，并且走 srng，不从雨流里借次数。

禁止

  • 在 splash 与 drips 之间插入新系统
  • 调换 mist / ripples 顺序
  • 让新功能从 this.rng 多抽，却放在闪电读数之前

结果：整关 drip 边缘、水花位置、旧捕获全部漂移。

允许

  • 新子系统 fork(专用盐)
  • 构建步骤追加在序列尾部
  • 空间哈希 / Noise(坐标) 代替顺序骰子

结果：旧 A/B 与 canary 仍有意义；Critic 评的是你改的东西。

// 雨块：harbor 原序，不可重排
this._buildRoofMask(ctx, wp);
if (wp.rain > 0.001) {
  this._buildRain();
  this._buildSplash();
  this._buildDrips(ctx);
  this._buildMist();
  this._buildRipples(ctx);
}
if (wp.lightning > 0) this._buildChannel();

// 雪：追加在末尾 + 使用 srng
if ((wp.snow || 0) > 0.001) {
  this._buildSnow();
  this._buildSnowAir();
}

9. 映射回 Build / Critic / Fix Agent

随机数不是“搜最优”，而是契约；本案例是契约被破坏后又被修回去。

角色 在本例中的动作 RNG 纪律
Build 实现雨 + 闪电捕获场景 应用 seed；当时误用单流
Critic / Verify 重拍 lightning、看指标、发现“退步” 暴露：A/B 比较了两场不同的雷
Fix fork lrng / srng；冻结雨序；雪追加在尾 结构修复，不调 seed 碰运气

给下一轮 Fix agent 的可执行规则（本例提炼）

  1. 先读 Art Direction 与 Published Contracts，再改密度 / 数量。
  2. 改密度前：问「多出来的 next() 落在哪条流？会不会动到 flashDir？」
  3. 新系统：先 fork(唯一盐)，再写生成逻辑；构建步骤只允许末尾追加。
  4. Verify 对齐 Critic 纪律：自有 --tag 重拍；改无关旋钮后确认 lightning 方位未漂。
  5. Finding 写法对齐 schema：一 owning file + 可测量 issue + 具体 fix（见 §3）。
关卡 PCG（树、破布、道具散落）用同一套思想： 模块 seed ^ 盐、空间 hash(ix,iz)、fork 子系统—— Critic 才能把「多一片板根 / 多一块布」与「整关被洗牌」区分开。
