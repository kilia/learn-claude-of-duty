## 1. 循环是什么

工作按编排好的 agent 波次推进，而不是单人自审自改：

```
Phase 1  BUILD     N 个 agent 并行，一人一文件（或一关两文件）
Phase 2  CRITIQUE  M 个对抗式 Critic，各自视觉镜头，对照已发售 AAA
Phase 3  FIX       按 finding 的 owning file 回派，仍一人一文件
Phase 4  VERIFY    单 agent 重拍、跑指标、诚实汇报
```

**创造（Build）**  
关卡 / 道具 / 渲染模块的 owner 按 `ARCHITECTURE.md`、`LEVELS_ROSTER.md`、各关 Art Direction 与上一轮 findings，生成或修改程序化几何、贴图、灯光与环境。

**审查（Critique）**  
独立 agent，不继承 Fixer 的截图；自有 `--tag` 重拍；对照 shipped title 打分；产出结构化 findings。

**修复（Fix）**  
把 Critic 的 verdict **原文嵌进** task，附上可测量诊断与指定文件的技术补救；禁止“再好看一点”式空指令。

Findings 按 **owning file** 路由，同一波次同一文件只有一个 writer——这是大规模并行的并发原语。

## 2. 项目约束与质量合同

### 2.1 硬约束（违反即废构建）

| 约束 | 原因 |
|------|------|
| 无 Node / bundler；经典 `<script>` + IIFE | 可从 `file://` 运行 |
| 无 `fetch` / 外部资源；一切程序化 | 零资源包体 |
| 仅 `window.THREE` 核心 + `window.GAME` | 无 examples/jsm |
| **禁止 `Math.random()`**，只用 `GAME.RNG` / `ctx.rng` | 捕获必须可复现，否则 critique A/B 无意义 |
| 不抛异常出构造 / build / update；不声明全局 | 捕获与 playtest 稳定性 |
| 颜色空间：albedo sRGB；normal/rough/metal/AO 线性 | 材质标定 |

### 2.2 质量即时拒收（ARCHITECTURE §9）

对照真实 COD 级截图。直接否决包括但不限于：

- 平面无纹理 / 单色表面  
- 明显贴图 tiling  
- 硬边锯齿阴影或 acne  
- 曝光爆白或死黑压碎  
- 灰盒子枪械；白球枪口焰  
- 胶囊体敌人；空洞无道具 / 磨损的几何  
- 过分笔直、干净、均匀的一切  
- 死气沉沉、无大气纵深的照明  

目标气质：**grounded, gritty, photographic, with atmospheric depth.**

### 2.3 关卡名单与 Art Direction

- **名单合同**：`LEVELS_ROSTER.md`（每关一句身份 + 光照 / 天气 / 色板）  
- **单关靶图**：如 `ART_DIRECTION_HARBOR.md` 中的 *The shot we are chasing*  
- **Instant-fail list**：比“做好看”可执行得多  

没有统一靶图时，14 个各自“好看”的模块会合成一张不连贯的画面。

### 2.4 提示词如何生效（方法摘要）

| 技术 | 作用 |
|------|------|
| 书面绑定合同先于代码 | 并行模块可首次集成 |
| 单一共享靶图（Art Direction） | 收敛审美 |
| 约束写成后果（“file:// 所以不能 fetch”） | agent 能外推 |
| Instant-fail 列表 | 可核对否决 |
| 可测量验收（亮度、grade_split…） | 可门禁 |
| 上轮 findings 写入下轮 brief | 跨无记忆的 agent 世代积累知识 |
| 显式 anti-overcorrection | 避免矫枉过正 |

用户侧总意图见 `PROMPTS.md`：fan-out、harsh critic、`/loop`、与 COD 盲比，直到过关。

## 3. 贴图管线（创造侧）

### 3.1 Height-first

程序化 PBR 的核心决策：**先写高度场，再派生其它通道**。同源高度保证 albedo / normal / roughness / AO 彼此不矛盾，磨损读起来像物理而非“画上去的”。

典型顺序：

1. 大尺度色调 / 基体噪声（fbm）  
2. 材料结构（Worley 骨料、ridged 裂纹、剪切条纹、砖/瓦晶格等）  
3. 磨损与污染掩码（湿渍、刮痕、生物附着…）  
4. 可选 deband  
5. `_emit`：AO、Sobel 法线、ORM 打包 → `DataTexture`  

噪声族：`fbm` / `worley` / `ridged` / `drip` / `shear` 等；配方在 `textures.js` 的 `gen*` 中。

### 3.2 晶格噪声与调用顺序无关

`Gen.lattice(fx, fy, salt)` 由 `(seed, fx, fy, salt)` 决定，**与调用顺序无关**——中间多加一层不会把后续层的随机场整体平移。这是贴图侧与顺序 RNG 流不同的隔离方式。

### 3.3 Wear 顶点色合同（与几何交汇）

`materials.js` 在 `vertexColors: true` 时把几何 `color` 读作 **磨损掩码**：

| 约定 | 含义 |
|------|------|
| 白 | 完好 |
| **R** | grime（污垢压暗） |
| **G** | wet（湿膜） |
| **B** | edge wear（棱边磨损 / 剥落） |

Dirt / wear 的空间分辨率受网格细分限制；贴图负责材料尺度，几何台阶（板缝、浮雕）必须是 mesh。

### 3.4 审查侧曾抓住的贴图级高价值缺陷

（图里看不见或指标易漏，靠读源码 / 探场景）

- 材质表把 roughness 钳在 ≥0.60 → 全库“粉笔感”、镜面全无  
- 五种专用贴图每帧生成却被名字重定向丢掉 → 沙袋穿着市集遮阳布  
- 覆盖率 / tiling 门禁本身不可靠（曾撤回）→ 指标必要但不充分

## 4. 几何 / Mesh 管线（创造侧）

### 4.1 原子与组装

常见原子：`bevelBox`、`cyl`、`tube` / `limb`、高度场、浮雕盒、扫掠、回转、实例化等。  
关卡用 `Builder` 按**材质桶**收集零件 → `Geo.mergeAll` → 顶点着色 → 少数静态 mesh。

### 4.2 树干（丛林）逐步拼装

复现 `level_jungle.js`：

1. 参数与轴线（高、半径、lean）  
2. `stations`：`[x,y,z,r]`，尖削 + lean + fbm 扭摆  
3. 半径圆盘  
4. 局部标架 N / B / T  
5. 截面环顶点  
6. `tube()` 扫掠成管壁三角  
7. `flute` 角向调制半径 → 纵向凹槽（打破“水管”圆截面）  
8. `buttressFin` 板根鳍片绕根旋转  
9. 全部进 `bark` 桶，finalize 时与其它树干合并；叶冠另路 InstancedMesh  

### 4.3 Bayon 浮雕脸（程序化雕刻）

复现 `level_ruins.js`：

- `faceHeight(u,v)`：高原 + 穹顶、眉弓与 undercut、闭眼睑、宽嘴、耳垂等  
- 相对塔身 **脚部半宽** 注册（对 mid 半宽注册会把下巴埋进石头）  
- 浮雕深度约 `fw * 0.160`  
- 局部 concavity 写入 wear：深度 AO 看不见的唇缝 / 睑缝靠凹度变暗  

**贴图救不了缺几何**：只有噪声的塔没有 Bayon 剪影；只有脸 albedo 贴片没有侧光浮雕。

### 4.4 板缝是几何（平行课）

`level_bunker.js` 的 `boardMarks`：模板缝是 ~12 mm 台阶，拉杆锥是 ~30 mm 凹坑。`SURF.wall_conc` 声明“模板混凝土”但若没有这些几何，3–10 m 只剩 tiling。Critic 曾指出 `boardMarks` 只到 y=6.40 而天花板 11.00 → 镜头对着的墙 42% 无缝；Fix 是把缝接到顶，不是再调 UV。

### 4.5 储油罐等工业组装

罐壳、焊缝、管嘴、抗风圈、锥顶、螺旋梯、围堰等分步扫掠 / 布尔式拼装，同属“原子 → 分步 → 材质桶合并”模式（见 Demo）。

## 5. Draw Call 合并与动态（布料 / 风）

### 5.1 “~18–20 draws” 指什么

通常指**关卡静态合并后的材质桶 mesh 数**，不是整帧（阴影、道具、后处理后常为数百 draw）。  
**主分割键是表面 / 材质桶**；透明、自发光、贴花另计；需要每实例变换 / 颜色时用 `InstancedMesh`。  
**不按“会不会飘”分割**——飘动另有路径。

### 5.2 静态合并 vs Flutter

普通 `mergeAll` 只保留 position / normal / uv，**丢掉 `aFlex`**。  
布料进 `clothParts`，经 **`mergeFlex`** 保留 `aFlex`，材质用 `applyWind` 注入顶点位移。

### 5.3 布料几何（Snowbound `K.sheet`）

1. UV 网格 `(nu+1)×(nv+1)`  
2. `pin(u,v)`：钉住权重（栅栏破布：上缘钉死、下摆自由）  
3. 静态 sag：只在 slack 区下垂（建造态，不是动画）  
4. `aFlex = slack²`  
5. 三角化  
6. `_clothPart` 登记（不进静态桶）  
7. `mergeFlex`  
8. `WIND_BODY`：顺风 lean + 多层正弦；振幅 ∝ `aFlex × gust`  
9. 每帧只更新 `sbTime` / `sbWind` / `sbWindDir`  

风速上升时振幅与频率同升——只抬一个会像慢动作。

### 5.4 市场遮阳等

许多 awning 是**静态下垂造型**，不是运行时风；与 cloth 风动路径不同。

## 6. 审查侧：Critic Agent

### 6.1 角色设定（Round 4 原文精神）

> You are a **BRUTALLY HARSH art director** who has shipped AAA shooters.  
> Grade against a **shipped title**, not against this level's own past, and **do not inflate for effort**.

### 6.2 强制动作

- 用**自己的** `--tag` 全套重拍（overview / hero1–3 / interior / firefight 等）  
- 全尺寸读 PNG；拟批评处再看 **2×**  
- 跑 `analyze.py`；门禁用可靠键（如 `dead_cell_med_pct`，不用已饱和的 `dead_cell_pct`）  
- 批评前 **读源码 / 探 live scene graph**  
- `hero1` 打最严  
- 回答是否仍被**共享渲染系统**卡住  

### 6.3 输出 Schema

```
level, score (0–100), verdict, presentable (boolean),
movedSince…, biggestRemainingGap, sharedSystemStillBlocking?,
findings[]: { file, severity, issue, fix }
```

- **一 finding → 一 owning file → 一具体技术补救**  
- “It feels flat” 不合格；要写到函数、高度、比例、测量数字  

历史上 **从未有关卡 `presentable: true`**；L1–L2 四轮后约 49–52 平台。

### 6.4 与 Fixer 结构分离（疤痕规则）

| 规则 | 失败教训 |
|------|----------|
| 不同 agent，不自评 | 自评评意图不评像素 |
| 自有 tag 重拍 | 继承 Fixer PNG = 审对方声称 |
| 1× + 2× 读图 | 碎石 / 漂浮落叶在 100% 不可见 |
| 读源码 | 最高价值发现在图外 |
| 对照 shipped title | 否则分数漂移、画面不动 |
| 结构化 finding | 否则 Fix 无法执行 |

### 6.5 Fix brief 如何写成

下一轮 task **粘贴 Critic verdict 原文**，再跟测量过的诊断、预算余量、anti-overcorrection、VALIDATE / 重拍命令清单。  
例（炼油厂）：*“you have built a refinery and then lit it like a car park.”* + 分区暖冷像素统计 + 灯 Rig 改法。

### 6.6 客观指标半边

`analyze.py`：曝光、死区、高光裁切、边密度、grade_split、单元可读性等。  
**必要但不充分**：关卡可全过门禁仍 32–38 分（身份缺失、无照明设计等）。  
错误门禁比没有门禁更糟（曾撤回“假 tiling”门禁；`dead_cell_pct` 饱和曾制造虚假全绿）。

## 7. 确定性与随机流纪律

### 7.1 目的

固定 seed → 同一 `(scenario, t, seed)` 同一帧。  
Critic A/B 只应反映**被测代码差分**，不是另一组运气。  
**Build/Fix 不搜“最优随机数”**；好看来自结构、参数与测量后的定点修改。

### 7.2 `fork(salt)`：派生且不推进父流

```js
RNG.prototype.fork = function (salt) {
  return new RNG((this._s ^ Math.imul(salt | 0, 0x9E3779B1)) >>> 0);
};
```

子系统（武器、闪电、雪、关卡模块）各自 fork。父流与其它子系统的抽取序列不变。

### 7.3 其它隔离

| 手段 | 作用 |
|------|------|
| 模块 `seed ^ 盐` | 关卡 / props / audio 互不 reshuffle |
| 空间哈希 `hash(ix,iz)` / Noise(坐标) | 与插入点无关 |
| 顺序流上 **冻结调用序** | 重排 = 整关 drip/splash 漂移 |
| 新能力 **末尾追加** + 新流 | 雪挂在雨块之后且走 `srng` |

### 7.4 典型事故（见 §8）

Splash rate ↑ → 主 RNG 每帧多抽 N 次 → 闪电 bearing 整段错位 → 两张 `lightning` 捕获是两场雷 → 指标动了却与 splash 无关 → **A/B 无效**。

## 8. 病例甲：Harbor Splash → Lightning（RNG 隔离）

### 8.1 Art Direction 交点

`ART_DIRECTION_HARBOR.md`：

- 靶图：凌晨两点集装箱码头、暴雨、钠灯体积光锥、积水涟漪；每隔数秒 **冷蓝白闪电** 冻结雨丝并投出与灯不同方向的硬影  
- Lightning：3–8 s 间隔、60–180 ms、~7000 K、**真阴影**  
- Instant-fail：Lightning as full-screen white fade with no directional shadow change  
- 最重要效果：灯锥穿过雨幕  

### 8.2 Weather Published Contract

`GAME.Weather` **独占**合同；他者只读。核心字段：

`wetness` · `rainIntensity`（仅液态；暴雪必须为 0）· `windDir` / `windSpeed` · `flash` / `flashDir` · `fogDensity` · `setPreset` · `strike()`  

扩展：`snowIntensity` · `precipIntensity` · `precipitation`  

非 harbor 上 preset 为 `clear` = **缺席**（不生成几何/贴图/灯），保护 Market canary。

交付物：雨丝体积、splash、涟漪、真方向闪电、镜头雨滴、滴水等。

### 8.3 循环时间线

1. **Build**：雨 / splash / 闪电曾共享顺序流  
2. **Critique / Verify**：只调 splash，lightning 方位与指标全变 → 误判“splash 伤了闪电”  
3. **Fix**：构造函数内、首次 `next()` 前 `lrng = fork(0x71A5)`、`srng = fork(0x53A0)`；雨块顺序冻结；雪末尾追加  
4. **Verify**：改 splash / flake 不再移动闪电日程  

三环咬合：Art Direction 要真闪电 → API 发 `flashDir` → RNG 保证同 seed 可复现。串流打断的是第三环。

## 9. 病例乙：Bayon 浮雕人脸（Mesh + Wear）

### 9.1 Brief

`LEVELS_ROSTER.md` · ruins：**Carved faces** 写在第一句；关卡名即 Bayon。  
石材需水渍、生物附着、崩边、差异侵蚀；黎明地雾、塔间神光。

### 9.2 Critic verdict（原文要点）

> "The Bayon face. Everything else on this list is a defect; this one is the level's **identity failing**."

- 五个已发布 framing 中 **没有任何浮雕脸**  
- Round 3 的 `faceTower` 是合格砌石（分层锥台、jog、grime）——**但没有脸**  
- 要求：眉弓、闭眼、阔鼻、宽而宁静的嘴、冠饰；20 m 可读、3 m 仍成立；放在镜头已对准处并让浮雕吃光  
- 本关 dead-region **门禁可通过** 仍 38 分 → 指标必要不充分  

### 9.3 Fix

- `faceHeight` 高度场 → 浮雕三角网  
- 相对 **foot 半宽** 注册；控制 inset / `fdp`  
- 凹处 concavity → 顶点 wear（R/G 压暗眼窝与切口）  
- 故意消耗三角形（当时有大量余量）  

结果：38 → 43，tris **+77.4%**；脸**存在**；Critic 仍可能读成 soft low-poly 而非完美砂岩——循环消**缺席**，不自动产**杰作**。

## 10. 循环能做什么、不能做什么

| 能 | 不能 |
|----|------|
| 发现并路由**可定位缺陷**（缺脸、缝不到顶、灯 Rig 倒置、RNG 串流） | 凭空写出“美的瞬间”指令 |
| 抬地板（最差关提升往往大于最优关） | 无限抬天花板（平台约低五十多分） |
| 用测量防止矫枉过正 | 用错误门禁制造虚假全绿 |
| 共享系统先修，解锁多关 | 代替作者设计照明与构图叙事 |

收益递减：多轮后边际增益变小；继续同一循环不等于突破平台。

## 结语

创造—审查—修复循环的本质是：

1. **书面合同**（架构、名单、Art Direction、发布字段）让并行创造可对齐；  
2. **可复现捕获 + 对抗审查**把“代码能跑”接到“画面是否违约”；  
3. **结构化 findings** 把审查变成下一轮可执行的定点修复；  
4. **确定性与流隔离**保证审查评的是差分本身；  
5. **几何与贴图各司其职**——身份剪影与毫米级台阶是 mesh，风化与湿污是贴图 / wear，缺失时不能互相冒充。  

仓库内 Demo 页是上述机制的可视化教具；两份 Critic 病例报告则是循环在真实缺陷上的完整录像。
