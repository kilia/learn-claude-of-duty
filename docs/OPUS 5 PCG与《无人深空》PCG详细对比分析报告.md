# OPUS 5 PCG 与《无人深空》PCG 详细对比分析报告

> 版本：v1.0  
> 日期：2026-08-07  
> 对比合同：[PCG对比Contract.md](PCG对比Contract.md)

## 摘要

OPUS 5 PCG 与《无人深空》PCG 的共同本质，可以概括为：

> 一个根 Seed 驱动一棵分层、确定性、受规则约束的内容生成树，并在运行时将它转化为可渲染的完整场景。

两者都不是简单的“随机撒点”，也不是单独的地形生成器。Seed 会沿着生成图传播，影响宏观环境、区域/群系、地形或几何、物体变体、材质、天气和运行时效果。噪声、空间坐标、哈希、参数化构件、模板和规则共同决定最终结果。

两者最重要的差异，不是生成规模，也不是一个生成星球、另一个生成 FPS 场景。真正值得比较的是：

1. PCG 是否承担了全部资产生产，还是与基础美术资源混合使用；
2. Seed 除了确定世界身份，是否还承担实验、回归和因果隔离职责；
3. 作者意图是由人工预先编码，还是由 LLM/Agent 从自然语言转译为生成器；
4. 系统是否需要支持玩家修改和持久化世界状态；
5. PCG 如何与 Mesh、LOD、流式加载、缓存和实时渲染结合；
6. 质量反馈是否能够反向修改生成器本身。

本报告首先确认两者共同的 PCG 基础，然后按合同逐项展开六个差异维度，最后给出对 OPUS 5 研究的启示和仍需验证的问题。

## 1. 研究范围与证据边界

### 1.1 比较对象

本报告中的 OPUS 5，指本项目 README、两份逐字稿、survey 文档和演示材料所整理出的 OPUS 5 端到端实验：

```text
自然语言 Art Direction
  → Agent 架构与任务拆分
  → 程序化几何 / 材质 / 布局 / 运行时
  → 固定 Seed 生成场景
  → Build → Critic → Fix → Verify
```

本报告中的《无人深空》，指 Hello Games 已公开展示和本项目第三方对照材料中所描述的 PCG 体系，重点包括：

- 单 Seed 与确定性世界生成；
- 地形、体素/密度场和 Mesh 重建；
- 群系、植被、生物和物体摆放；
- 程序化材质与基础资源的混合；
- LOD、GPU 环境对象、程序化 Mesh、纹理流式加载和运行时性能。

### 1.2 证据等级

本报告使用三种证据标记：

- **已观察/已整理**：来自本目录 README、survey 和演示说明。它们可以支持研究判断，但未必等同于原始源码审计。
- **公开资料确认**：来自 Hello Games 官方更新说明和 GDC Vault 等公开一手资料。
- **待验证推断**：根据结果、公开演讲或项目整理材料推断出的内部机制，尚未由完整源码确认。

项目 README 已明确说明：OPUS 5 原始生成工程中的 `src/...`、`docs/...`、`ARCHITECTURE.md` 等文件目前不在本目录。因此，OPUS 5 的具体函数、参数和调用关系仍不能表述为源码级事实。[项目 README](README.md)

同样，本项目的《无人深空》文档是第三方对照整理，不应把其中所有算法名称、体素尺寸、存储格式或内部调用关系都直接视为 Hello Games 官方确认的实现。

### 1.3 两项明确不作为本质差异

根据合同，以下两项不单独作为核心差异：

#### 生成规模不同

规模属于应用目标和运行时压力差异。只有当规模具体导致 Seed 组织、状态保存、流式加载、LOD 或缓存机制不同，才在运行时契约中讨论。

#### 生成核心不同

星球、体素地形、FPS 场景、建筑、生物等内容类型自然会导致几何算法不同。不能仅凭“生成的东西不同”就判断两套 PCG 的方法论不同。

例如，OPUS 5 使用扫掠、车削、挤出和高度场，不能直接与《无人深空》的体素 Mesh 重建做“谁更先进”的比较。更有意义的问题是：两种算法是否都承担了确定性、规则约束、可组合、可渲染和可维护的职责。

## 2. 统一抽象：单根 Seed 驱动完整场景

### 2.1 “单根 Seed”的准确含义

本报告采用以下统一定义：

> 一个根 Seed 作为整棵内容生成树的入口，最终影响场景布局、地形或几何、物体变体、材质、天气/环境以及渲染结果。

这并不意味着系统内部只有一个随机数流。完整系统通常包含：

```text
rootSeed
  ├─ levelSeed / levelRng
  ├─ regionSeed / biomeSeed
  ├─ objectSeed
  ├─ materialSeed
  ├─ weatherSeed
  └─ coordinate / spatial hash
```

因此后续必须区分两个概念：

| 概念 | 含义 |
|---|---|
| 单根 Seed | 整个场景拥有一个统一的可追溯起点 |
| 单一 RNG 流 | 所有系统共用一条按调用顺序消耗的随机序列 |

前者是两者的共同点；后者并不是好的工程实现。OPUS 5 的材料明确强调通过 `fork(salt)`、局部 Seed 和空间哈希避免所有系统共享同一条顺序随机流。

### 2.2 OPUS 5 的 Seed 传播

根据本项目整理，OPUS 5 的 Seed 进入系统后大致经过以下路径：

```text
URL / 运行参数中的 seed
        ↓
GAME.RNG 与 GAME.Noise
        ↓
Level / Props / Materials / Weather / Weapons / AI
        ↓
关卡计划、物体 Seed、材质配方、天气日程
        ↓
几何原子、贴图纹理、Mesh 合并和动态对象
        ↓
浏览器中的最终画面
```

OPUS 5 的一个显著特点是，Seed 不只是控制“场景长什么样”，还控制“测试是否具有因果意义”。同一个 `(场景, 时间, Seed)` 应该产生相同结果，这样 Critic 对两个版本截图的比较才主要反映代码变化，而不是随机数变化。

### 2.3 《无人深空》的 Seed 传播

本项目第三方材料将《无人深空》概括为单 Seed 驱动从星系、星球到地表内容的生成体系。公开的一手资料可以确认，《无人深空》以数学方式生成大规模世界、地形和程序化艺术；GDC Vault 对 Sean Murray 演讲的介绍明确将主题描述为：使用数学生成真实和外星地形，并在小团队条件下创建和测试无限环境。[GDC Vault：Building Worlds Using Math(s)](https://www.gdcvault.com/play/1024514/Building_Worlds_Using_Math%28s%29)

更细的内部 Seed 分层，例如星系、恒星系统、星球、区块和坐标之间究竟采用何种派生公式，目前不能仅凭公开资料确认。因此可以确认的是：

- Seed 是世界生成的稳定输入；
- 生成内容与空间位置和世界层级相关；
- 系统需要能够在玩家重新访问时恢复同一个世界；
- 具体的 Seed 派生树和随机流实现仍属于待源码验证内容。

### 2.4 两者的共同结构

两者都可以抽象成：

```text
根 Seed
  → 环境身份
  → 区域/群系规则
  → 地形或空间结构
  → 内容对象与变体
  → 材质与细节
  → 运行时对象与渲染
```

这说明“单 Seed 生成整个场景”不是一个展示层说法，而是架构层约束：如果材质、布局、天气和物体各自脱离 Seed，就无法真正做到场景级复现。

## 3. 共同点一：确定性重建

### 3.1 确定性不是“每次都一样”这么简单

PCG 中的确定性至少包含四个层次：

1. **输入确定**：Seed、场景参数、时间、坐标和生成器版本确定。
2. **计算确定**：同一输入经过同一规则，得到同一中间数据。
3. **依赖确定**：新增或修改一个局部系统，不会无故扰动无关系统。
4. **输出确定**：最终几何、材质、运行时状态和截图可以重复获得。

因此，更严谨的表达不是：

```text
seed → scene
```

而是：

```text
(generatorVersion, rootSeed, sceneConfig, timeState, coordinate)
    → reproducibleResult
```

如果生成器版本改变，即使 Seed 不变，结果也可能变化。对游戏来说，版本更新有时必须改变世界；对回归测试来说，则必须保留版本信息以便判断差异来源。

### 3.2 OPUS 5 中的确定性用途

OPUS 5 的确定性主要服务三件事：

#### 场景复现

从一个 Seed 启动，可以重新生成同一个关卡、同一批物体、同一套材质和同一组天气效果。

#### Critic A/B

如果修改前后各自抽到不同的物体位置、闪电位置或材质噪声，Critic 无法判断差异来自代码还是随机性。固定 Seed 将评价从“重新抽到的另一张图”变成“同一场景在代码修改前后的差异”。

#### 局部修复不拖动全局

OPUS 5 材料中的典型事故是 Splash 和 Lightning 共用顺序 RNG。修改 Splash 的抽样次数后，Lightning 位置整体变化，导致 A/B 失去因果意义。

正确做法是：

```text
weatherRoot
  ├─ splashRng = fork("splash")
  ├─ lightningRng = fork("lightning")
  └─ snowRng = fork("snow")
```

这样，Splash 内部增加随机抽样，只影响 Splash，不影响 Lightning。

### 3.3 《无人深空》中确定性的主要用途

对《无人深空》而言，确定性首先是世界身份和空间寻址机制：玩家可以在同一宇宙中重新访问已经见过的星球和地点，系统不能每次加载都生成另一个世界。

确定性还支持：

- 玩家之间共享同一地点；
- 服务器或客户端重新构造环境；
- 不保存每个最终 Mesh 的情况下恢复世界；
- 生成结果与坐标、星球属性、群系规则保持一致。

《无人深空》的确定性更接近“世界地址协议”，OPUS 5 的确定性则额外接近“实验与回归协议”。

### 3.4 共同点与差异总结

| 问题 | OPUS 5 | 《无人深空》 |
|---|---|---|
| Seed 是否决定场景身份 | 是 | 是，公开资料支持这一总体判断 |
| 是否需要重复生成相同结果 | 是 | 是 |
| 确定性是否服务于玩家重新访问 | 当前材料未重点覆盖 | 是核心需求之一 |
| 确定性是否服务于 A/B 测试 | 是核心需求 | 公开材料未显示有同等 Agent Critic 机制 |
| 是否需要避免局部修改污染无关结果 | 明确要求 fork、salt、空间哈希 | 方法论上需要，但内部隔离实现待验证 |

关键结论是：两者共享确定性 PCG 的基础，但确定性的“工程消费者”不同。OPUS 5 的主要消费者是 Agent 迭代闭环；《无人深空》的主要消费者是稳定世界和运行时重新构建。

## 4. 共同点二：分层生成与生成树

### 4.1 为什么需要分层

完整场景无法由一个公式直接生成。无论是 OPUS 5 还是《无人深空》，都必须把生成任务分成多个层次：

- 宏观身份：荒漠、雨林、冰雪、工业港口等；
- 空间结构：区域、地形、路线、边界、坡度、水体；
- 内容类别：建筑、植被、矿物、生物、道具；
- 形态细节：参数化几何、骨架、部件和局部变体；
- 表面细节：高度、法线、粗糙度、颜色、污渍和磨损；
- 运行时表现：风、雨、雪、雾、LOD、实例化和后处理。

分层的价值在于：

1. 控制依赖关系；
2. 保证内容语义一致；
3. 允许局部替换；
4. 便于性能优化；
5. 便于测试和修复。

### 4.2 OPUS 5 的分层方式

OPUS 5 更像“从艺术方向向下展开”的生成树：

```text
Art Direction
  → 关卡名单 / 质量合同 / 文件 Owner
  → 区域、路线、防线、POI、镜头目标
  → 建筑、树、罐体、布料、雕像、道具
  → 几何原子与材质桶
  → 贴图配方与顶点磨损
  → 合批、实例化、风动和渲染
```

它的顶层不是一个自然环境参数，而是一个由人类语言描述的“场景身份”。例如，Art Direction 不只是规定“有树”，还规定主光、天气、色板、标志物和镜头中必须可读的身份特征。

### 4.3 《无人深空》的分层方式

《无人深空》的分层更像“从宇宙寻址向下展开”：

```text
宇宙 / 星系 / 星球身份
  → 星球环境与群系
  → 地表高度、密度或体素场
  → 植被、矿物、建筑和生物分布
  → 生物/物体模板与部件变体
  → 材质、颜色、天气和运行时效果
```

本项目第三方材料进一步整理了地形、物体摆放、Superformula、L-System、骨架蓝图和群系查表等机制。但这些具体实现的完整内部来源仍需谨慎标注。公开资料可以确认 Hello Games 的生成目标覆盖地形和程序化艺术，并且后续版本继续对地形、植被、生物、云、风和水系统进行整体更新。

### 4.4 共同方法论

两者都把 Seed 传播到不同层级，而不是让所有内容直接读取同一个随机数：

```text
rootSeed
  → layerSeed
  → regionSeed
  → objectSeed
  → local variation
```

分层也意味着内容不是独立生成的。例如：

- 材质要知道物体属于什么表面类型；
- 植被要知道群系、坡度、湿度和高度；
- 建筑要知道所在区域和路线；
- 天气要知道环境身份；
- LOD 要知道对象类别和观察距离。

所以，PCG 的关键不是拥有很多算法，而是能否把算法组织成稳定的生成依赖图。

## 5. 共同点三：确定性随机、噪声与空间哈希

### 5.1 三类变化机制

两套系统都可以将变化来源分成三类：

#### 全局变化

由根 Seed 或环境 Seed 控制，例如不同星球、不同关卡或不同天气主题。

#### 局部离散变化

由对象 ID、区域 ID、盐值或空间哈希控制，例如第 17 棵树的倾角、某个网格里的岩石类型。

#### 连续空间变化

由 Perlin、FBM、Worley、Ridged 或其它噪声场控制，例如地形起伏、污渍强度、岩石密度和植被分布。

可以抽象为：

```text
value(x, y, z)
  = rule(
      globalSeed,
      spatialNoise(x, y, z),
      hash(regionId, objectId, salt),
      semanticParameters
    )
```

### 5.2 OPUS 5 的实现重点

OPUS 5 survey 对这部分的整理比较明确：

- 项目禁止 `Math.random()`；
- 系统级随机通过 `fork(salt)` 隔离；
- 贴图使用 FBM、Perlin、Worley、Ridged、Drip、Shear 等噪声或结构算子；
- 贴图尽量用 Seed 加空间坐标决定采样；
- 物体的局部扰动优先绑定对象私有 Seed；
- 格子哈希避免新增一个对象就推移后续所有对象的随机序列。

这一策略的核心是“修改局部生成器，尽量只影响局部输出”。

### 5.3 《无人深空》的对应原则

《无人深空》的公开和项目整理材料同样体现出：地形、物体分布和生物群系不应完全依赖每次启动时的顺序随机，而要与空间位置、环境类型和规则有关。

例如，植被和建筑摆放需要满足：

- 位置在可接受地形上；
- 分布密度符合群系；
- 物体不会全部重叠或形成均匀棋盘；
- 同一地点重新访问时保持一致。

项目对照材料将这类逻辑归纳为网格偏移、2D 噪声密度、Biome Lookup 和规则化分组。具体数据结构和函数名称仍应视作对照材料中的技术归纳，而不是已确认源码。

### 5.4 关键差异：顺序确定性与空间确定性

这两类确定性经常被混淆：

| 类型 | 特征 | 优点 | 风险 |
|---|---|---|---|
| 顺序 RNG | 第一次调用得到第一个值，第二次调用得到第二个值 | 实现简单，适合阶段性随机 | 插入一次调用会拖动后续所有结果 |
| 空间哈希/坐标噪声 | 输出由坐标、Seed、盐值决定 | 与调用顺序弱相关，适合流式加载和局部修改 | 需要设计哈希、边界和连续性 |

OPUS 5 明确把两者结合：高层阶段可以使用独立顺序流，贴图和大量空间扰动尽量使用空间采样。对《无人深空》而言，空间相关确定性尤其重要，因为玩家可能从任何方向、任何时间加载一个区域。

### 5.5 结论

两者的共同点不是都使用某一个特定噪声函数，而是都遵循：

> 用 Seed 定义身份，用空间和对象 ID 定义位置，用噪声定义连续变化，用规则定义允许的结果。

## 6. 共同点四：规则约束随机性

### 6.1 为什么纯随机不够

纯随机可以迅速生成数量，但通常会产生四类问题：

1. 结构上不合理：物体穿插、漂浮、悬空或无法行走；
2. 生态上不合理：植被、地形、湿度和气候互相矛盾；
3. 视觉上不合理：没有构图、标志物和层次；
4. 游戏上不合理：路线不可读、POI 不可达、战斗空间不可用。

因此两者都需要把“随机”放在一个由语义规则限定的空间里。

### 6.2 OPUS 5 的规则层

OPUS 5 的规则层主要来自两部分：

#### 艺术和关卡规则

- 区域、路线、防线、层级和镜头目标先确定；
- 建筑、道具和杂物根据区域语义生成；
- 关键标志物必须在指定镜头中可读；
- 场景要符合 Art Direction 的主光、天气和色板。

#### 几何和材质规则

- 储油罐的身份来自罐壳、焊缝、加强筋、平台、梯子和围堰等结构；
- 树干先确定轴线、站点、局部标架和截面，再生成管状几何；
- 布料通过 pin、sag 和 `aFlex` 确定哪里固定、哪里摆动；
- 高度场是 Normal、AO、Roughness、Metalness 等材质通道的共同来源；
- 顶点色承担 grime、wet、edge wear 等空间语义。

这说明 OPUS 5 的规则不是单纯的“概率表”，而是包含结构、材质、运动和镜头身份的质量合同。

### 6.3 《无人深空》的规则层

根据项目第三方整理和公开展示，《无人深空》的规则层主要包括：

- 星球或区域类型；
- 地形模板和地形特征权重；
- 坡度、高度、温度、湿度等环境变量；
- 生物群系查表；
- 网格化偏移和密度规则；
- 生物、植物、矿物和建筑的候选集合；
- 生物或复杂物体的模板、骨架和部件组合。

官方 2024 年更新说明也展示了这种“环境变量—内容系统—运行时效果”的联动：云覆盖会随星球、时间和天气变化；风系统同时影响树、叶、烟、雨、雾和雪；水体状态受到天气和水深影响；程序化生物、植物和地形系统继续共存于同一行星环境中。[Worlds Part I 官方更新说明](https://www.nomanssky.com/worlds-part-i-update/)

### 6.4 两者的共同点

两者都在解决同一个问题：

> 如何让随机变化看起来像一个有环境逻辑的世界，而不是互相独立的随机样本。

因此可以把两者都看作“规则系统包裹随机系统”，而不是“随机系统产生规则”。

### 6.5 差异的真正位置

差异不在于一方有规则、另一方没有规则，而在于规则的来源和表现方式：

- 《无人深空》的规则主要由开发团队提前设计并固化在系统中；
- OPUS 5 的规则还需要由 Agent 从自然语言 Art Direction 解释出来，并分配给不同代码模块。

这会在后面的“作者意图进入生成系统”部分展开。

## 7. 共同点五：程序化内容与运行时渲染结合

### 7.1 PCG 不是离线数据生成器

一个场景即使能够通过数学公式生成，也不代表它能在游戏中正常工作。PCG 必须同时处理：

- 几何拓扑；
- 材质通道；
- 阴影和光照；
- 动态对象；
- 实例化与合批；
- 远近距离变化；
- 生成、缓存和销毁时机；
- 玩家修改后的重建。

所以两者都属于“生成—渲染一体化”的 PCG，而不是只生成一个静态模型。

### 7.2 OPUS 5 的生成—渲染连接

OPUS 5 的材料展示了一个相对紧凑的浏览器运行时管线：

```text
Noise / Recipe
  → Height
  → Normal / AO / Roughness / Metalness
  → DataTexture / 材质缓存
  → PBR + Triplanar + Detail / POM / Wet
```

几何则经过：

```text
参数化原子
  → Builder 收集
  → 按材质 / 表面语义分桶
  → mergeAll
  → 少量静态 Mesh
```

动态对象单独走：

```text
实例对象 → InstancedMesh
布料 → mergeFlex + aFlex + 顶点着色器风动
粒子/天气 → 独立运行时系统
```

OPUS 5 的一个重要工程原则是“按材质/表面语义合批，而不是简单按是否动态分类”。普通静态合并会丢失布料所需的逐顶点动态属性，因此布料必须保留独立路径。

### 7.3 《无人深空》的生成—渲染连接

《无人深空》公开更新说明明确将 PCG 与引擎性能放在一起描述：

- 树、岩石和草等环境对象转向 GPU-based 系统；
- 远距离行星对象拥有更高质量的 LOD 表现；
- 地形生成采用 dual marching cubes voxel meshing；
- 该改动旨在减少顶点、加快地形生成、提升帧率并节省内存；
- 系统还对纹理流式加载、LOD 生成和程序化 Mesh 进行了整体优化。

这说明《无人深空》的 PCG 不是“先生成一张地图，再交给引擎”，而是从数据表示开始就考虑 Mesh、内存和运行时更新。[Worlds Part I 官方更新说明](https://www.nomanssky.com/worlds-part-i-update/)

### 7.4 共同点的核心

两者都需要回答同一个问题：

> 生成出的内容如何以足够低的成本进入实时画面，并且在变化、移动和重新加载时保持稳定？

区别主要是运行时契约的复杂度和实现规模，而不是是否需要运行时渲染。

## 8. 共同点六：用规则和参数压缩最终内容

### 8.1 规则压缩的基本模型

传统手工内容通常接近：

```text
每个场景 / 每个物体 / 每张贴图
  → 单独制作并存储最终结果
```

PCG 更接近：

```text
生成器 + 参数 + Seed + 少量基础资源
  → 需要时生成最终结果
```

这并不意味着程序化内容不需要艺术资源，而是将资源从“每个最终实例”压缩成“可复用的基础样本、模板和规则”。

### 8.2 OPUS 5 的极限方向：代码即美术资源

OPUS 5 的研究目标是：

- 0 预制贴图；
- 0 预制 Mesh；
- 不依赖外部美术文件；
- 启动时由代码生成内容。

因此，OPUS 5 中的程序化系统同时承担了三种角色：

1. 资产格式：几何和纹理由代码表达；
2. 资产生成器：代码将参数转化为视觉内容；
3. 资产装配器：Builder、材质桶和运行时系统将内容装入场景。

这是一种很激进的“生成器优先”生产模式。

### 8.3 《无人深空》的混合模式

本项目第三方材料将《无人深空》归纳为：基础样本、纹理集合、模板/蓝图与运行时程序化修改的混合模式。

这种方式的优势是：

- 可以保留艺术家对基础形态和材质的控制；
- 生成器只需要负责变体、组合和环境适配；
- 复杂生物、飞船和建筑不必完全由数学原语从零构造；
- 可以在视觉质量和内容数量之间取得平衡。

因此，两者都用规则压缩内容，但压缩对象不同：

| 系统 | 主要压缩对象 |
|---|---|
| OPUS 5 | 甚至把基础几何和基础材质也压缩成代码算子与配方 |
| 《无人深空》 | 将大量实例压缩成 Seed、模板、部件、材质样本和环境规则 |

---

## 9. 差异一：资产来源策略

### 9.1 OPUS 5：零外部资产的生成器优先

OPUS 5 的材料明确把“0 贴图、0 Mesh、0 外部美术资源”作为实验前提。这个前提带来的不是简单的资源节省，而是整个生产链的变化：

```text
艺术目标
  → 生成几何的算法
  → 生成材质的算法
  → 场景组合
  → 运行时渲染
```

艺术家要表达一个储油罐，不是交付一个储油罐 Mesh，而是交付“罐壳、板层、焊缝、加强筋、平台、梯子、围堰”等结构语义；Agent 再将这些语义写成几何原子和组装规则。

### 9.2 《无人深空》：程序化系统与基础资产结合

《无人深空》的内容生态需要大量具有身份辨识度的生物、植物、矿物、建筑和飞船。项目第三方材料将其描述为基础样本、纹理集合、骨架蓝图、部件和程序化变形的组合体系。

这里的关键并不是“《无人深空》没有 PCG”，而是它将 PCG 放在基础资产之上：

```text
艺术家基础样本 / 模板 / 部件
  → Seed 与环境规则选择
  → 缩放、组合、变形、着色
  → 程序化变体
```

### 9.3 方法论差异

两种资产策略对应不同的作者成本：

| 维度 | OPUS 5 | 《无人深空》式混合模式 |
|---|---|---|
| 初始资源依赖 | 极低 | 需要基础样本和模板 |
| 单个新物体的生成成本 | 需要设计生成器和语义组装 | 可以增加部件或样本后复用已有生成器 |
| 艺术家直接控制最终轮廓 | 较弱，需要通过参数和规则表达 | 较强，基础样本可以直接提供形态身份 |
| 变体数量 | 理论上高 | 取决于模板、部件和组合规则 |
| 生成器维护成本 | 较高 | 生成器与资产库共同承担 |
| 风格稳定性 | 依赖配方和 Agent 是否理解艺术方向 | 依赖基础资产和规则的风格边界 |

### 9.4 不能简单得出的结论

“零资产”不等于“艺术成本为零”。它只是把成本从制作最终资源转移到：

- 几何原语设计；
- 材质算子设计；
- 参数调节；
- 语义命名；
- 生成器测试；
- 视觉验证。

相反，基础资产也不等于不使用 PCG。它只是让程序化生成可以从更高质量、更稳定的形态先验开始。

### 9.5 初步判断

OPUS 5 探索的是“程序化生成器本身可以成为美术生产格式”；《无人深空》更接近“基础美术资产由程序化系统放大、组合和适配”。

这不是谁更先进的问题，而是两种不同的成本迁移方式。

## 10. 差异二：Seed 的工程用途

### 10.1 共同基础

两者都需要 Seed 保证：

- 世界身份稳定；
- 场景可重新生成；
- 空间内容与位置一致；
- 规则和参数的变化可以被追踪。

### 10.2 《无人深空》：Seed 作为世界身份和地址

对《无人深空》来说，Seed 的第一职责是“这个世界是什么”。它需要让玩家能够：

- 进入同一个星球；
- 在同一个环境中重新找到同类内容；
- 与其它玩家共享发现；
- 在程序不保存全部最终几何的情况下恢复环境。

这使 Seed 接近一种内容地址：

```text
seed + universe coordinates
  → planet identity
  → local terrain / objects / environment
```

具体的宇宙坐标到 Seed 的内部映射尚待源码或官方技术资料进一步验证，但“Seed 服务于世界身份和重新访问”是合理的系统级判断。

### 10.3 OPUS 5：Seed 作为实验控制变量

OPUS 5 在此基础上增加了软件工程职责：

```text
固定 Seed
  → 固定场景
  → 固定截图
  → Critic 找到差异
  → Fix 修改局部生成器
  → Verify 回归
```

如果 Seed 只被当作“换一张图的旋钮”，它无法支持严肃的 Agent 迭代。OPUS 5 因此强调：

- 禁止 `Math.random()`；
- 新增系统使用独立 fork；
- 修改中间物体不能多抽共享父流；
- 新系统应追加在旧阶段末尾；
- 局部随机尽量使用物体 Seed 或空间哈希。

### 10.4 Seed 工程职责的差异表

| Seed 职责 | OPUS 5 | 《无人深空》 |
|---|---|---|
| 生成场景身份 | 是 | 是 |
| 支持地点重建 | 目标之一 | 核心要求 |
| 支持多人/跨设备共享世界 | 当前材料未覆盖 | 是重要应用场景 |
| 支持截图 A/B | 核心要求 | 未见同等公开机制 |
| 支持局部修改不污染无关结果 | 明确写入工程纪律 | 方法上需要，细节待验证 |
| 作为 Agent 回归测试变量 | 是 | 未见同等公开机制 |

### 10.5 结论

OPUS 5 没有发明“Seed 决定世界”这一思想。它的新重点是把 Seed 从内容身份扩展为：

> 生成器的测试协议、变化的因果边界和 Agent 迭代的控制变量。

## 11. 差异三：作者意图如何进入生成系统

### 11.1 《无人深空》：人工设计规则，程序执行规则

《无人深空》的公开 GDC 描述强调数学、程序员生成的世界和艺术，而不是让语言模型实时设计生成器。[GDC Vault：Building Worlds Using Math(s)](https://www.gdcvault.com/play/1024514/Building_Worlds_Using_Math%28s%29)

其生产链可以抽象为：

```text
设计师 / 程序员
  → 定义模板、参数、群系、分布规则和性能约束
  → 实现生成系统
  → 调参、测试、发布和迭代
```

作者意图会被写入：

- 生物群系规则；
- 地形模板；
- 基础样本和部件库；
- 颜色和材质配方；
- 生物/物体组合限制；
- 性能和内容密度参数。

这种方式的优势是规则长期稳定、可控、可调试；缺点是规则设计和维护需要专门的技术、美术和工具团队。

### 11.2 OPUS 5：自然语言成为生成器的上游输入

OPUS 5 的特殊性在于，输入不是一个已经实现的生成器，而是类似：

```text
偏 3A 的艺术方向
场景身份
天气和主光
关键标志物
资源限制
```

Agent 需要把它连续翻译为：

```text
Art Direction
  → 架构
  → 文件和模块分工
  → 几何算子
  → 材质配方
  → 场景布局
  → 运行时渲染
  → Critic 规则
```

这意味着 OPUS 5 的研究对象不只是 PCG 算法，而是“自然语言到生成系统”的编译过程。

### 11.3 两者的共同基础

自然语言不会凭空生成一个好场景，传统 PCG 也不会凭空理解艺术方向。两者都需要把高层审美意图转换为可执行约束：

- 场景身份是什么；
- 哪些物体必须出现；
- 物体如何组合；
- 哪些材质应该形成对比；
- 光照和天气如何服务身份；
- 哪些结果应当被拒收。

### 11.4 OPUS 5 增加的风险

Agent 参与生成器设计会带来新的不确定性：

1. 语言意图可能被错误解释；
2. Agent 可能只实现“物体存在”，没有实现视觉身份；
3. 生成器接口可能缺乏稳定性；
4. 不同 Agent 可能违反同一套约束；
5. Critic 可能把审美问题误判成曝光或参数问题；
6. 多轮修复可能改变未被要求修改的区域。

OPUS 5 通过质量合同、文件 Owner、结构化 finding、固定 Seed 和 Verify 来降低这些风险。

### 11.5 结论

《无人深空》展示的是“人设计生成器，程序大规模执行”；OPUS 5 试图推进到“Agent 参与设计生成器，人通过合同和 Critic 监督结果”。

这是两者之间最具有时代差异的一点。

---

## 12. 差异四：世界状态与可编辑性

### 12.1 纯重建与持久化世界不是同一问题

固定 Seed 可以重新生成一个基础世界，但并不自动解决玩家修改：

```text
基础世界 = Generate(seed)
玩家修改 = Edit(world)
重新加载 = Generate(seed) + Replay(edits)
```

如果玩家挖掉一座山、建造一个基地或改变一个物体，系统必须决定：

- 修改是否永久保存；
- 修改如何覆盖程序生成结果；
- 修改数据如何与版本兼容；
- 修改区域如何重新生成 Mesh、碰撞和材质；
- 其它玩家如何看到同样状态。

### 12.2 《无人深空》的状态契约

《无人深空》属于需要处理持久化世界状态的系统。官方更新说明在介绍 2024 年地形变化时，特别说明底层地形形状没有重置，已有基地不会被移动。这说明生成系统必须遵守一项兼容性契约：新版本可以扩展视觉和内容，但不能随意破坏已有世界状态。[Worlds Part I 官方更新说明](https://www.nomanssky.com/worlds-part-i-update/)

因此其状态模型至少可以抽象为：

```text
稳定基础生成结果
  + 玩家建造 / 地形修改 / 发现记录
  + 版本兼容策略
  + 重新加载与网络同步
```

具体的存储格式和回放算法不在当前公开材料中，不能进一步断言。

### 12.3 OPUS 5 当前状态

OPUS 5 当前材料主要验证：

- 给定 Seed 可重建同一场景；
- 修改生成器后可以做截图 A/B；
- 局部随机不会拖动无关结果；
- 构建、审查、修复可以重复执行。

尚未验证：

- 玩家挖掘或破坏地形；
- 玩家摆放并永久保存建筑；
- 程序生成结果与人工修改的覆盖关系；
- 版本升级后的状态迁移；
- 网络或多客户端一致性。

### 12.4 方法论差异

两者都需要“基础 Seed 世界”，但《无人深空》还需要“基础世界之上的可持续状态层”。这使它的 PCG 不能只追求每次重新生成一致，还必须追求：

```text
生成一致性
+ 修改可记录
+ 修改可合并
+ 版本可兼容
+ 状态可同步
```

OPUS 5 的后续研究如果要从 Demo 走向游戏系统，必须补上这一层。

---

## 13. 差异五：运行时契约

### 13.1 运行时契约的定义

这里的“运行时契约”不是简单的场景大小，而是生成系统必须对引擎承诺什么：

- 何时生成；
- 生成多少；
- 如何缓存；
- 如何进入渲染；
- 如何切换 LOD；
- 如何处理玩家移动；
- 如何应对世界修改；
- 如何在版本更新后保持稳定。

### 13.2 OPUS 5 的运行时契约

OPUS 5 当前运行在浏览器 3D 环境，主要特点是：

- `file://` 或轻量浏览器环境即可运行；
- 启动时由代码生成内容；
- 不依赖外部美术资源；
- 静态几何按材质桶合批；
- 重复对象使用 `InstancedMesh`；
- 布料保留 `aFlex`，通过顶点着色器实现风动；
- 材质使用程序化纹理、PBR、AO、雾和后处理。

其优势是：

- 结构简单；
- 结果易复现；
- 生成器容易被 Agent 修改；
- 对小型场景的端到端演示成本低。

其限制也已经在 README 中明确：

- 场景尺度较小；
- LOD 不完整；
- 裁剪和遮挡剔除不充分；
- 完整物理仿真不足；
- 某些光照效果依赖特定镜头成立；
- 静态合批和动态系统之间需要人工维护边界。

### 13.3 《无人深空》的运行时契约

《无人深空》官方更新说明显示，其运行时契约包含：

- GPU-based 环境对象渲染；
- 远距离对象的 LOD 表现；
- dual marching cubes voxel meshing；
- 地形生成速度、顶点数量、帧率和内存之间的平衡；
- 纹理流式加载；
- 程序化 Mesh 生成优化；
- 统一的风系统；
- 既有地形和基地的兼容性。

这套契约不仅要求“生成出几何”，还要求生成器能在玩家移动、观察距离改变、天气变化和世界更新时持续工作。

### 13.4 两者的对照

| 运行时问题 | OPUS 5 | 《无人深空》 |
|---|---|---|
| 生成时机 | 主要是启动和场景构建阶段 | 需要持续加载、更新和优化 |
| 静态几何 | 按材质桶合批 | 程序化 Mesh、LOD、GPU 环境对象 |
| 重复对象 | `InstancedMesh` | GPU/实例化/LOD 等成熟运行时机制，具体内部实现待验证 |
| 动态风动 | 布料 `aFlex` + Shader | 官方说明中有统一风系统 |
| 地形修改 | 当前未验证 | 需要与既有基地和世界状态兼容 |
| LOD/流式 | 当前不充分 | 官方明确提到 LOD、纹理流式和程序化 Mesh 优化 |
| 运行环境 | 浏览器 Demo | 成熟商业游戏引擎和多平台运行时 |

### 13.5 关键结论

两者都把 PCG 视为运行时系统，但 OPUS 5 当前更接近“可验证的生成—渲染闭环”，《无人深空》更接近“长期运行、可修改、可流式加载的世界基础设施”。

## 14. 差异六：质量审查与迭代流程

### 14.1 OPUS 5 的 Build → Critic → Fix → Verify

OPUS 5 的流程不是单纯地让 Agent 生成一次代码，而是：

```text
Build
  → 独立 Critic 截图、读源码、按质量合同评价
  → 结构化 finding
  → 回派到 owning file 的 Fix Agent
  → Verify、回归和重新截图
```

Critic 的输出包括：

- `score`；
- `verdict`；
- `presentable`；
- `findings[]`；
- 对应文件、函数或模块；
- 可执行的修复目标。

### 14.2 Critic 解决的主要问题

OPUS 5 的 Critic 特别擅长发现三类问题：

#### 缺席

名单要求有某个标志物，但场景中根本没有。例如“塔有了，但 Bayon 脸的身份没有出现”。

#### 违约

场景违反资源、命名、运行环境、Seed 或输出格式约束。

#### 可定位缺陷

问题可以落到具体文件、函数、材质配方或生成阶段，而不是停留在“感觉不够好”。

### 14.3 《无人深空》的已知迭代方式

从公开资料可以确认 Hello Games 长期持续对地形、云、风、水、植被、程序化 Mesh、LOD 和纹理流式系统进行版本迭代。例如 2024 年官方更新同时描述了新的环境表现和底层引擎优化。

但当前公开资料没有足够证据证明其存在与 OPUS 5 类似的：

- 独立视觉 Critic Agent；
- 结构化 finding 回派；
- 自动修改生成器；
- 固定 Seed 下的多 Agent 自我修复闭环。

因此，本报告不把“《无人深空》没有 Critic”写成绝对事实，而是写成：

> 当前可获得资料没有显示《无人深空》使用与 OPUS 5 同类型的 Agent 化 Build → Critic → Fix 流程。

### 14.4 两种迭代模式

| 方面 | OPUS 5 | 《无人深空》式成熟开发流程 |
|---|---|---|
| 生成器的作者 | Agent 与人类共同产生 | 专业程序、美术和设计团队 |
| 反馈来源 | Critic、截图、源码、指标和质量合同 | 人工测试、设计评审、玩家反馈、性能数据和版本迭代 |
| 修复目标 | 可回派到 owning file | 由团队定位到系统、资源或版本改动 |
| Seed 作用 | 控制实验变量 | 保持世界身份和兼容性 |
| 主要风险 | Agent 误解意图、随机污染、局部修复破坏全局 | 系统复杂、手工调参成本高、版本兼容成本高 |

### 14.5 Critic 的边界

OPUS 5 自身材料也强调：Critic 擅长消除缺陷，不保证自动产生艺术杰作。

这可以推广到两套 PCG 系统：

```text
规则约束可以提高下限
确定性可以提高可控性
大量变体可以提高内容数量
但视觉品质仍取决于生成器、参数、镜头和作者判断
```

因此，Agent Critic 是生产闭环创新，不是艺术质量的充分条件。

## 15. 各类算法的可比性：哪些能直接比，哪些不能直接比

### 15.1 可以直接比较的方法论问题

- 是否有单根 Seed；
- Seed 是否传播到完整场景；
- 是否能够确定性重建；
- 随机流是否隔离；
- 是否依赖空间坐标；
- 规则如何约束随机性；
- 生成器如何与渲染器结合；
- 是否支持局部修改；
- 质量反馈是否能回到生成器。

### 15.2 不能直接以“算法强弱”比较的问题

#### Dual Marching Cubes vs 参数化扫掠

一个主要用于从密度/体素场提取可编辑地形，一个主要用于从轴线、截面和语义参数构建物体。应比较它们的可控性、拓扑、性能和适用边界，而不是比较谁更先进。

#### Triplanar vs Height-first

Triplanar 主要解决纹理投影和 UV 问题；Height-first 主要解决材质通道之间的共同结构来源。它们可以同时存在，不是同一层算法。

#### Gielis/L-System vs 几何原子

Superformula、L-System、骨架蓝图和 OPUS 5 的 `tube`、`bevelBox`、扫掠原子，都属于“把语义结构参数化”的方法，但具体表达能力不同，不能仅凭名字判断优劣。

### 15.3 更合适的比较单位

后续应使用“职责”而不是“算法名称”比较：

| 职责 | 比较问题 |
|---|---|
| 身份生成 | 如何让不同 Seed 产生不同但可控的场景身份 |
| 空间生成 | 如何保证地形、物体和群系的空间一致性 |
| 结构生成 | 如何表达树、建筑、生物或地貌的连续形态 |
| 表面生成 | 如何保证高度、颜色、粗糙度和磨损关联 |
| 运行时生成 | 如何更新 Mesh、LOD、缓存和动态效果 |
| 质量控制 | 如何发现坏结果并改进生成器 |

## 16. 总体对照矩阵

| 对比维度 | 共同基础 | OPUS 5 特征 | 《无人深空》特征 | 当前判断 |
|---|---|---|---|---|
| 根 Seed | 单根 Seed 驱动完整生成树 | Seed 同时服务于 A/B 与 Agent 回归 | Seed 更强调世界身份和地点稳定 | 共同基础相同，工程消费者不同 |
| 确定性 | 同一输入可重建同一结果 | 强调 fork、salt、空间哈希和调用顺序隔离 | 需要空间一致和世界重访，内部隔离待验证 | OPUS 5 的测试纪律更明确 |
| 分层生成 | 宏观到局部逐层展开 | Art Direction → 关卡 → 几何/材质 → 渲染 | 宇宙/星球 → 群系 → 地形 → 生物/物体 → 渲染 | 结构相似，顶层语义不同 |
| 随机性 | 随机受规则、坐标和语义参数约束 | 噪声配方和几何局部 Seed 较突出 | 环境变量、群系和空间分布较突出 | 方法论相同，算子组合不同 |
| 资产 | 用规则减少最终资源 | 目标是零预制 Mesh/贴图 | 基础样本/模板与程序化变体混合 | 资产策略不同 |
| 作者意图 | 都要把审美变成规则 | LLM/Agent 从语言生成系统 | 人工团队预先实现系统 | 生产方式不同 |
| 世界状态 | 都需要基础生成结果稳定 | 当前主要验证重新生成 | 需要玩家修改、基地和版本兼容 | 状态模型不同 |
| 运行时 | 生成与渲染一体化 | 浏览器、合批、实例化、Shader 风动 | GPU 对象、体素 Mesh、LOD、流式和性能优化 | 运行时契约不同 |
| 质量闭环 | 都需要调参和验证 | Build → Critic → Fix → Verify | 传统团队迭代，Agent 化闭环待证 | 质量生产方式不同 |

## 17. 对 OPUS 5 研究的主要启示

### 17.1 “单 Seed”必须升级为“可审计的生成图”

仅仅在入口接收一个 `seed` 不足以证明系统可复现。需要能够回答：

- 哪个模块读取了根 Seed；
- 哪些模块使用了派生 Seed；
- 哪些对象依赖坐标哈希；
- 哪些阶段仍然依赖顺序 RNG；
- 修改某个模块会影响哪些输出；
- 生成器版本和材质版本是否被记录。

建议将未来的 Seed 记录组织为：

```text
GenerationManifest
  ├─ generatorVersion
  ├─ rootSeed
  ├─ sceneConfigHash
  ├─ systemSalts
  ├─ materialRecipeVersion
  ├─ objectSeedPolicy
  └─ temporalState
```

### 17.2 Agent 可调用的 PCG 算子必须具有稳定接口

OPUS 5 当前已经整理出 Texture、Geometry、Layout、Runtime 四类算子。要进一步接近工业 PCG 系统，每个算子应明确：

- 输入参数；
- 输出数据；
- Seed 依赖；
- 空间尺度；
- 可组合约束；
- 性能成本；
- 失败模式；
- 可视化样例；
- 是否允许持久化修改。

例如，一个可被 Agent 调用的 `buildTree` 不应只返回 Mesh，而应返回：

```text
TreeResult {
  geometry,
  materialBuckets,
  collisionProxy,
  localSeed,
  bounds,
  lodHints,
  dynamicChannels,
  semanticTags
}
```

### 17.3 “零资产”需要与“零先验”区分

OPUS 5 的零预制资产目标很有研究价值，但不应把它误解为完全不需要先验。

先验可以以多种形式存在：

- 几何原语；
- 材质噪声算子；
- 结构规则；
- 色板和 Art Direction；
- 参数范围；
- Critic 质量合同；
- 可复用的生成器接口。

未来比较时应衡量的是：

> 先验到底以 Mesh、纹理、模板、代码、参数还是质量合同的形式存在。

### 17.4 Critic 应评价“生成系统”，不只评价一帧画面

OPUS 5 当前 Critic 已经开始读源码和看截图。进一步可以加入 PCG 特有指标：

- Seed 稳定性；
- 局部修改影响范围；
- 跨区域接缝；
- 生成时间；
- Mesh 顶点数；
- 材质桶数量；
- LOD 切换质量；
- 重建后状态一致性；
- 相邻区域连续性；
- 变体多样性与重复率。

这样 Critic 才能从“这张图好不好看”升级为“这套生成器是否可持续”。

### 17.5 需要补充持久化状态研究

如果 OPUS 5 未来要与《无人深空》这类完整游戏 PCG 系统进行更深比较，必须验证：

```text
Generate(seed)
  → 玩家修改
  → 保存局部差异
  → 重新生成基础世界
  → 叠加差异
  → 保持 Mesh、碰撞、材质和状态一致
```

这会把研究从“确定性生成 Demo”推进到“可持续运行的 PCG 世界”。

## 18. 仍需验证的问题

### 18.1 OPUS 5 待验证

需要拿到原始生成工程后确认：

1. 根 Seed 是否真的覆盖所有运行时系统；
2. `fork(salt)` 的具体实现是否始终不推进父流；
3. 哪些材质噪声使用空间哈希，哪些仍使用顺序 RNG；
4. 贴图配方是否全部由同一 Seed 参与；
5. 合批后的顶点属性是否在所有动态路径中正确保留；
6. 场景布局是否具有真正的导航和碰撞约束；
7. LOD、裁剪和遮挡剔除的实际覆盖率；
8. Critic 发现是否能稳定回到 owning file；
9. 多轮 Agent 修复是否会出现跨模块回归；
10. 生成器版本、材质版本和 Seed 是否共同记录。

### 18.2 《无人深空》待验证

当前公开材料不足以确认：

1. “单根 Seed”在内部具体如何分层；
2. 星系、星球、区块和坐标之间的派生公式；
3. Dual Marching Cubes 的完整实现和适用边界；
4. 地形体素、材质属性和玩家修改的存储结构；
5. 生物、植物、建筑和飞船是否共用统一的 Seed 层级；
6. 基础资产、模板和程序化生成之间的确切边界；
7. LOD、流式加载和 GPU 环境对象的内部调度；
8. Hello Games 内部是否有类似自动 Critic 的工具链。

### 18.3 证据使用原则

在没有源码或官方技术文档时，报告可以说：

- “公开资料表明”；
- “项目对照材料整理为”；
- “从系统目标推断”；
- “需要源码确认”。

不应直接说：

- “官方源码一定使用某某函数”；
- “所有内容都由某一个算法生成”；
- “某个公开社区逆向结果就是完整实现”。

## 19. 结论

### 19.1 共同本质

OPUS 5 和《无人深空》都属于 Seed 驱动的分层 PCG 系统：

```text
根 Seed
  → 环境身份
  → 空间与规则
  → 内容结构
  → 表面材质
  → 运行时渲染
```

它们共同依赖：

- 确定性；
- 分层生成；
- 噪声与空间采样；
- 规则约束随机；
- 生成器与渲染器结合；
- 用规则、参数和基础资源压缩内容。

### 19.2 OPUS 5 的主要新增点

OPUS 5 的独特性不在于重新发明某个地形、噪声或材质算法，而在于将以下环节连接起来：

```text
自然语言艺术目标
  → PCG 生成器
  → 运行时场景
  → 独立 Critic
  → 结构化 Fix
  → 确定性 Verify
```

也就是说，OPUS 5 的研究重点是：

> 让 Agent 不只是调用 PCG 算法，而是参与设计、实现、测试和修复 PCG 系统。

### 19.3 《无人深空》的主要参考价值

《无人深空》为 OPUS 5 提供的最重要参照不是某一个具体公式，而是成熟 PCG 系统必须面对的工程问题：

- 世界可寻址；
- 结果可重建；
- 规则和随机性可控；
- 生成结果与渲染性能结合；
- 地形、材质、生物和环境互相协调；
- 玩家修改和版本更新不能轻易破坏既有世界。

### 19.4 最终比较判断

两者可以用一句话区分：

> 《无人深空》把确定性 PCG 做成了一个可长期运行、可探索、可维护的世界基础设施；OPUS 5 则尝试让 LLM/Agent 自动组织并写出这样的 PCG 生产闭环。

OPUS 5 真正值得继续研究的方向，不是简单复制《无人深空》的某个算法，而是把成熟 PCG 的关键职责沉淀为 Agent 可调用、可测试、可审查和可组合的生成器接口。
