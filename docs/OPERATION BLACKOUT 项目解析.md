# OPERATION BLACKOUT 项目解析

## 项目背景

根据 [README.md](D:/workspace/kelvin/operation-blackout/README.md)，这是一个用 Three.js r180 构建的第一人称射击游戏：10 个关卡、约 15.7 万行游戏代码、**零外部资源文件、零构建步骤**，双击 `index.html` 即可运行。没有一张 png/jpg/hdr/glb/mp3，所有纹理、网格、音效、天空全部由代码程序化生成。这个约束的成因很有意思：开发机器上没有 Node.js 和 npm，且 `file://` 协议封锁了所有运行时加载。

### 项目轮次

项目由多轮 AI agent 并行编排构建（约 4340 万 token、156 次 agent 运行），根目录的 8 个 md 文件正是这套 agent 协作体系的"沟通协议"。

围绕这张表的补充细节：

- **被中断的第 2 轮**：Claude Code 订阅的速率限制导致 20 个 agent 中 12 个中途死亡。恢复时 8 个已完成的从缓存重放、只重跑 12 个死掉的——这就是该轮“花了 3.78M token 却无产出”的原因（写入文档 §10.2）。
- **成本换算**：按 90/10 输入输出比和 Claude Opus 5 API 价格估算约 $305；最坏情况（全按输出计价）约 $1,085。实际跑在订阅上，瓶颈是速率限制而非费用。
- **单关边际成本**（§10.3）：关卡 1 = 21.2M（含从零建引擎），关卡 2 = 12.7M（共享文件争用导致 10 倍成本），关卡 3–6 约 1.3M/关，关卡 7–10 约 1.0M/关且无需修复轮。
- **墙钟时间**：约 20 小时工作流执行，瓶颈是验证而非模型延迟（SwiftShader 软件光栅下单次无头截图要 1–4 分钟）。

每个阶段内部的组织方式（BUILD → CRITIQUE → FIX → VERIFY 四相流水线、批评打分、按文件所有权路由修复）在同文件第 5 节有方法论级描述，各轮批评分数表在 §5.5。仓库中没有保存更细粒度的单次 agent 运行日志或 prompt 逐条记录——原始提示词的浓缩版在 [PROMPTS.md](D:/workspace/kelvin/operation-blackout/PROMPTS.md)，提示词的结构模板在 writeup 的附录 B。

各关卡的详细介绍：

1. **Al-Bakr Market**：地中海南岸/中东风格战损集市街道，约 70m×14m，沿 −Z 延伸。两侧 2–4 层建筑，底层商铺带波纹雨棚和褪色条纹帆布。有可进入的小巷（深影+单束光+湿斑）、废弃商铺室内、可达屋顶，街中有烧毁轿车、沙袋工事、坍塌阳台等场景道具。
2. **Cold Harbor**：凌晨暴雨中的集装箱码头，约 90m×70m。核心是“湿”的视觉——积水如黑镜反射每盏灯。集装箱堆 2–4 层形成可攀爬的战斗峡谷，有跨码头龙门吊（可登高）、可进入仓库（屋顶破洞漏雨）、系泊货轮的黑色海面，钠灯光锥穿透雨幕是本关标志性效果。
3. **Kirovsk Pass**：暴风雪中的高山公路和半掩埋村庄。木质达恰别墅（屋顶积雪）、石砌教堂、抛锚卡车队、坍塌桥梁、消失在白化中的松林。雪是最难的材质：高亮但不曝光的反照率、半透明衰减、闪光颗粒、偏蓝阴影。
4. **Line 4 — Zarechnaya**：废弃被淹的地铁站和运行隧道。贴砖站台、坠落天花板、自动扶梯厅、可穿行的脱轨列车、积映应急灯条积水的隧道。完全无天空，每颗光子来自故障荧光灯、红色应急条和工作灯。
5. **Meridian Tower**：日落时的未完工摩天楼：开放楼板、裸露钢筋柱、风中作响的塑料布、塔吊、脚下延伸到地平线的城市。垂直性是全部要点——真实落差的开放边缘、脚手架、反射日落的玻璃幕墙段。
6. **AMARG Boneyard**：正午沙漠中的飞机存放场。成排收缩膜包裹的机身、拆解的机身段、堆叠发动机与机翼、热裂的停机坪。灼热顶光下短而硬的阴影、热浪扭曲、尘卷风；设计陷阱是画面扁平惨白，需用巨大机身投出的深荫来对抗。
7. **Facility K-17**：掩埋的冷战指挥设施。防爆门、布线槽的混凝土走廊、死寂 CRT 屏墙的控制室、反应堆画廊、被淹的下层。故障闪烁荧光灯、扫过墙壁的旋转红色警报信标、漫长的黑暗区段。
8. **Mekong Delta**：河流与废弃火力点周围的茂密热带丛林。分层树冠、林下植被、藤蔓、板状根、象草，光线被树冠过滤成斑驳光柱。湿热细雨、树干间雾气、叶片滴水、泥泞、腐烂沙袋、被植被回收的坠毁直升机。
9. **Zubair Refinery**：黄昏的石化工厂。蒸馏塔、管廊、栈桥走道、储罐，以及向一切投下真实动态火光的火炬烟。蒸汽排放、钠色泛光灯、危险条纹、虚构文字警告牌。主导意象是黄昏天幕下的复杂工业剪影，上方橙色火光、下方冷色泛光。
10. **Bayon Ruins**：黎明晨雾中被丛林吞噬的石庙群。雕刻面孔、坍塌回廊、撬开砌体的树根、苔藓地衣、庭院积水。低角度柔光穿透雾气，塔间长光束。全名册最安静的关卡，力量来自氛围与尺度。

补充一点设计原则：名册刻意让 10 个关卡钉死在昼夜、天气、光源、空间、材质的不同组合点上，任何两关都不共享外观；3–10 关采用声明式 `env` 配置驱动共享系统，无需改渲染代码。

## 文档体系的意义

这 8 个文件构成一套为 **AI agent 并行开发**设计的文档分工，各司其职：

| 层次    | 文档                                                        | 面向对象                |
| ----- | --------------------------------------------------------- | ------------------- |
| 是什么   | README.md                                                 | 人类访客/玩家             |
| 怎么协作  | ARCHITECTURE.md                                           | 所有编码 agent          |
| 画成什么样 | ART_DIRECTION.md、ART_DIRECTION_HARBOR.md、LEVELS_ROSTER.md | 编码 agent + 评审 agent |
| 怎么改   | DEVELOPMENT.md                                            | 任何修改代码的 agent       |
| 接力棒   | NEXT_ROUND.md                                             | 下一轮的 agent 编排者      |
| 为什么存在 | PROMPTS.md                                                | 历史存档                |

它的核心思想是：把"单一事实来源"拆分到维度上——架构契约管模块边界、美术方向管视觉收敛点、关卡名册管差异化设计、开发指南管变更安全、交接文档管轮次状态。由于每个文件只有一个 agent 拥有、其他 agent 只读，这套 md 文档实质上充当了无协调中心的多 agent 开发中的**分布式锁与共识协议**，这是它超越普通项目文档的意义所在。
